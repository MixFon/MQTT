# Миграция на новый VPS

Старый сервер (`mrmixfon.ru`) попал под блокировку ТСПУ по IP — переезжаем
на новый VPS. Домен остаётся тем же, меняется только IP за DNS-записью и,
как следствие, физический сервер, который держит все сервисы (см. «Что
установлено» в `VPS_NOTES.md`).

Сертификат Mosquitto выпущен на CN/SAN `mrmixfon.ru`, а не на IP — поэтому
сертификаты и CA переносятся со старого сервера на новый как есть, без
перевыпуска. Это значит, что прошивку ESP32 (она пинит конкретный `ca.crt`)
перепрошивать не нужно: устройства продолжат доверять тому же CA, изменится
только IP, на который резолвится домен.

Claude доступа к VPS не имеет (см. `CLAUDE.md`) — все команды ниже выполняются
пользователем вручную либо через `deploy/migrate.sh`.

## 2. Перенести сертификаты Mosquitto и базу данных

Со своей машины, имея SSH-доступ на оба сервера:

```bash
./deploy/migrate.sh user@old-vps-host user@new-vps-host
# либо через переменные окружения:
OLD_TARGET=user@old-vps-host NEW_TARGET=user@new-vps-host ./deploy/migrate.sh
```

Скрипт делает по порядку:
1. забирает `/etc/mosquitto/certs/*` и `/etc/mosquitto/passwd` со старого
   сервера, раскладывает на новом с правильными правами (`root:mosquitto`,
   см. раздел 3 `VPS_DEPLOY.md`)
2. забирает данные `sensor_readings` со старого сервера через `\copy ... TO
   STDOUT` (только строки таблицы, без служебных таблиц TimescaleDB)
3. на новом сервере убеждается, что таблица уже создана миграциями
   `iot-backend` (если сервис ещё ни разу не стартовал — запускает его на
   пару секунд ради миграций и останавливает), затем грузит данные через
   `\copy ... FROM STDIN`

Схема БД (таблица, hypertable) переносится не дампом, а создаётся заново
миграциями `iot-backend` на новом сервере — так же, как на старом. Через
`pg_dump`/`pg_restore` в custom-формате переносить всю базу нельзя: он
тащит с собой служебные таблицы расширения `_timescaledb_catalog.*`, формат
которых привязан к точной версии TimescaleDB, и если версии на старом и
новом сервере отличаются, restore падает с ошибкой вида `column
"schema_name" of relation "chunk" does not exist`.

Дамп и сертификаты проходят через временную локальную директорию (не
напрямую между VPS) — старому и новому серверу не обязательно быть видимыми
друг другу по сети.

Скрипт безопасно перезапускать целиком с начала — `TRUNCATE` перед загрузкой
данных делает восстановление идемпотентным.

После скрипта на новом сервере вручную:

```bash
sudo systemctl enable --now mosquitto
sudo systemctl status mosquitto
tail -f /var/log/mosquitto/mosquitto.log   # ошибки TLS/прав — сюда, не в journalctl

sudo systemctl start iot-backend
sudo systemctl status iot-backend
```

## 3. Проверить новый сервер

```bash
sudo systemctl status postgresql mosquitto iot-backend caddy --no-pager
curl -s https://mrmixfon.ru/api/rooms
mosquitto_sub -h localhost -p 8883 --cafile /etc/mosquitto/certs/ca.crt \
  -u iot -P <пароль> -t 'home/#' -v      # ждём, что реальный ESP32 начнёт публиковать
```

Проверить, что показания идут от реальных устройств (не только ручной
`mosquitto_pub`) — ESP32 должны сами переподключиться на новый IP по DNS,
без перепрошивки. Если устройство держит долгоживущее TCP-соединение или
закэшировало резолв — может понадобиться его перезагрузка.

## 4. Завершить работу на старом сервере

Выполнять только после того, как новый сервер стабильно принимает данные
от реальных датчиков хотя бы несколько дней — чтобы было время заметить
проблему и откатиться (старый сервер ещё жив и не тронут).

- [ ] Снять контрольный дамп на старом сервере на всякий случай:
      `sudo -u postgres pg_dump -Fc -d iot -f iot-final.dump` и скачать локально
- [ ] Остановить сервисы: `sudo systemctl stop iot-backend mosquitto caddy postgresql`
- [ ] Убедиться, что старый сервер больше не упомянут как актуальный
      (`mrmixfon.ru` в DNS уже не указывает на него — проверено в разделе «Статус»)
- [ ] Освободить/отменить аренду старого VPS
- [x] Обновить `VPS_NOTES.md`, если IP/хостинг изменились в описании сервера
